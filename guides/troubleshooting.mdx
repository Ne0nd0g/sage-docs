title: "Troubleshooting"
description: "Symptoms you may hit while installing and running Sage, what each one means, and where the fix is documented."
---

Each entry starts from what you see, explains the cause, and links to the page that owns the fix.
Check the Sage container log first: Sage names missing settings and failing paths there rather than
failing silently.

## The log does not show enough detail

Mythic runs installed services at the `warning` log level by default. Raise it to `debug` with
`sudo ./mythic-cli config set debug_level debug`, then `sudo ./mythic-cli restart sage`, and read
the output with `sudo ./mythic-cli logs sage`. To watch Sage in a terminal instead, run it from
source. See [Run from source and debug logging](/configuration/run-from-source#debug-logging).

## `unable to open database file` at startup

Sage's SQLite databases sit on a filesystem that does not support SQLite locking. This happens
when Mythic runs under Docker Desktop or OrbStack on macOS, where the bind-mounted service
directory goes through a file-sharing layer. Move the databases inside the container with two
`.env` lines: see [SQLite on macOS](/configuration/runtime-state#sqlite-on-macos).

## Autonomous solves are refused, or the BloodHound chip is not connected

The BloodHound chip shows `not configured` when no BloodHound URL or token is set for the chat, and
`unavailable` when BloodHound is configured but did not connect or did not answer a read; hover
over the chip for the reason. When a connect fails, the container log shows a `WARNING` that starts
`BloodHound auto-connect (chat):` and names the missing credentials, never their values. Sage does
not retry a credential set that already failed, and every later turn repeats the cause as
`Last failure: …`. Ordinary conversation and supervised chats keep working; autonomous solves fail
closed because they cannot plan without the graph. Fix the credentials and run `/bloodhound`: see
[When BloodHound is not connected](/guides/bloodhound#when-bloodhound-is-not-connected).

A bare `McpError: Connection closed` with no explanation means the Sage build predates that
diagnostic. Update Sage.

## BloodHound is connected, but graph collection fails or ingest is not ready

`/bloodhound` reports **Ingest** as not ready when the connected MCP server cannot report
ingest-job status. Sage then refuses to collect or ingest, reports **Collection failed** with the
dependency diagnostic, and shows a one-time notice in chat; graph reads still work. The image ships
the pinned MCP with Sage's ingest-status patch, so the usual cause is a stale image or a custom
checkout without the patch. Rebuild with `sudo ./mythic-cli build sage`, or patch your checkout and
run `/bloodhound force`. See [Ingest readiness](/guides/bloodhound#ingest-readiness).

## `/mcp connect` is refused before it connects

The connect request has no `sage_execution_class`, so it defaults to `unclassified` and is
refused. Add `"sage_execution_class":"non_target_control_plane"` to the request. See
[Connecting MCP servers](/guides/mcp-servers).

## An MCP tool always asks for approval, or is denied in conversation

MCP tools default to guarded. Classify read-only tools in `mcp_tool_policy.json`, and run
`/mcp policy` to confirm the effective classification. See
[Connecting MCP servers](/guides/mcp-servers).

## A guarded tool is missing or disabled

The channel's bot token lacks the scope Sage checks for that tool (`task.write`, `payload.write`,
`credential.write`, `file.write`, or `file.read`), so Sage disables the tool up front. Add the
scope to the bot token. If Sage reports no callbacks, output, or files that you can see in Mythic,
the token is missing a read scope. See
[Minimum bot token scopes](/reference/tools-and-capabilities#minimum-bot-token-scopes).

Builds before `v0.3.0` gated tasking on `callback.write` instead of `task.write`, so a token with
only `task.write` lost its tasking tools there.

## Conversation mode does not act, even with Autonomous Solve on

This is expected. Conversation mode stays read-only, and Sage ignores the Autonomous Solve toggle
there and says so once in the chat. Switch the channel to Supervised with `/mode supervised` to
approve actions one at a time. See [Authority modes](/understand/authority-modes).

## An approved task ended without a confirmed result

The task did not return a result before the wait deadline. Sage ends the request with the exact
Mythic task ID and an incomplete-observation notice, and does not re-issue the task. Its outcome is
unknown: inspect that task's output in a fresh request before approving another action. See
[Approving guarded actions](/guides/using-chat#approving-guarded-actions).

## Mythic shows a request as complete, but Sage stopped it

Mythic records only `complete`, `error`, and `cancelled` as a request's status, so a request that
Sage stopped on its own or that ended blocked can still show as `complete`. The final message
states how the request ended. Since `v0.3.0`, Sage also records it as `turn_outcome` in the final
message's metadata.

## After a restart, the channel accepts no new message

A restart leaves the request Sage was answering open in Mythic, and Mythic accepts no new prompt in
that channel until it ends. Sage closes or settles such requests when Mythic sends the container
its startup message, which Mythic sends only to an operation with an active bot account assigned to
it. Without one, use Cancel on the open request in Mythic to free the channel. See
[Requests a restart left open](/configuration/runtime-state#requests-a-restart-left-open).

## A Continue saved decision / Stop card appeared after a restart

You answered an approval card while Sage was down or starting, and Sage cannot tell whether Mythic
will still deliver that decision. It applies nothing until your original decision arrives or you
answer the new card. **Continue** applies the decision exactly as you made it (an approval runs the
action once, a rejection runs nothing); **Stop** discards it. If the card, the session, or the
paused action changed in the meantime, nothing runs and the request closes with the reason.

## Sage asks for a new chat after a restart

Since `v0.4.0`, an existing chat continues after a Sage restart and Sage says so in the channel.
Sage asks for a new chat only when the session ended on purpose (stop, cancel, an error, or a
changed configuration or API token), when its saved state cannot be read, or when a chat from
before restorable sessions cannot be matched to one saved conversation; the reply names which.
Archiving `sage.db` also removes every saved session. The Engagement State Ledger, `/state`, and
`/report` are unaffected. See
[What a restart does to your chats](/configuration/runtime-state#what-a-restart-does-to-your-chats).

## The provider rejects the chat's model or settings

When the provider refuses a request, for example a reasoning effort with tools on Chat Completions,
a Responses-only model on Chat Completions, or a Daybreak access error, Sage's error names the
setting to change, the value it sent and where that value came from, and whether the chat
continues. Changing **Model**, **OpenAI API**, **OpenAI Daybreak**, **OpenAI Safety Identifier**, or
**Reasoning Effort** keeps the conversation; a new API key, provider, or API endpoint starts a new
chat. See [When the provider refuses a request](/guides/models#when-the-provider-refuses-a-request).

## A reinstall fails on root-owned files

Sage `v0.2.0` writes some runtime state into the service directory as root, which can block a later
`mythic-cli install` by a non-root user. Archive that state with `sudo` before reinstalling. From
`v0.3.0`, Sage runs as the service directory's owner and hands root-owned files from earlier
versions back on first start. See [Clean resets](/configuration/runtime-state#clean-resets).

## Sage or the Phoenix UI stops responding

On `v0.2.0`, the Phoenix UI on port 6006 can freeze on its first request; `v0.3.0` fixes this. To
see where a running Sage is stuck, send the process `SIGUSR1` (`docker kill -s USR1 sage` for the
container): Sage writes every thread's stack to its log. Read it with
`sudo ./mythic-cli logs sage`.

## A trace has no model spans

Not necessarily a broken trace. In objective runs the policy can resolve every decision
deterministically, and the run then legitimately contains zero model spans. See
[Observability](/configuration/observability).
