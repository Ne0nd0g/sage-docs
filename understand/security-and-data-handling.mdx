This page summarizes the boundary documented in the Sage repository's
[`docs/SECURITY_AND_DATA_HANDLING.md`](https://github.com/MythicAgents/Sage/blob/main/docs/SECURITY_AND_DATA_HANDLING.md).
When this page and the repository document disagree, the repository document is authoritative.

## The control-plane boundary

- Sage may use Mythic and BloodHound control-plane data: callbacks, tasks, files, credentials,
  graph facts.
- All target-facing interaction executes as Mythic tasks on live payload callbacks. Sage never
  connects directly to target LDAP, SMB, Kerberos, WinRM, RPC, HTTP, or equivalent services, and
  Sage-local attack artifacts are not compromise proof.

## Evidence rules

- Runtime effects and objective completion require Mythic task output or artifacts, Mythic
  credential-store state, or BloodHound facts derived from payload-collected artifacts.
- Self-reported success is not proof. The [Engagement State Ledger](/understand/how-sage-works#the-engagement-state-ledger)
  records a hop as achieved only with a valid proof envelope.

## Data handling

- Do not put secrets in scripts, skills, logs, or public artifacts. `read_credentials` can place
  raw secrets in model context and traces; use it deliberately.
- Retained identity and membership observations are shared across assisted chats in the same
  Mythic operation engagement and persist across Sage restarts. `/report` shows what has been
  retained; a reported identity or host membership does not prove current authentication or access.
- The optional Slack hook emits only a fixed generic change notice: never operation, finding,
  host, user, domain, credential, task, or file values. Full findings stay in native Mythic chat
  inside your trusted deployment.
- Model providers receive everything a request carries, potentially including raw credentials, task
  output, and file content. Sage does not verify a provider's residency, training, or retention
  policy; disable provider logging or retention where your rules require it.
- On the direct OpenAI Responses route, Sage sends requests with `store: false` and replays the
  history and the model's encrypted reasoning itself. Each request also carries the
  [safety identifier](/guides/models#openai-safety-identifier), when you set one, and the selected
  [Daybreak](/guides/models#openai-daybreak) program. Other retention follows your OpenAI project's
  settings; projects with zero data retention that use Daybreak need Private Safety Processing. Use
  a named, non-default OpenAI project approved for the program, keep its API key in the `API_KEY`
  user secret or the container environment rather than plaintext chat configuration, and choose a
  stable pseudonymous safety identifier that is not a username or email address.
- `sage.db` keeps the state a chat needs to [continue after a restart](/configuration/runtime-state#what-a-restart-does-to-your-chats),
  including conversation messages and pending approvals. A paused request's saved state holds
  identities, counters, and digests, never text bodies or argument values. Restrict access to the
  file.
- After a restart, Mythic's short-lived startup token may read Sage's open chat requests and their
  approval cards, post a notice, close a request, or offer a decided card's saved decision as a
  Continue/Stop card, and is then discarded. It never runs a task or a model call, and it never
  applies a decision: only the original decision's own delivery, or your Continue on the channel's
  own token, can.
- The optional [coding-agent worker](/guides/coding-agent)'s API key sits in
  `container/codex/.env`, readable by anyone with Mythic access to Sage's files and by anyone with
  Docker access to the worker. In this release Sage sends the worker no prompt.
